# Особая прогулка с компанией — план изменений файлов и БД

Статус: первоначальный технический план. Актуальная реализация: [особая прогулка](GROUP_EVENT_IMPLEMENTATION.md). Требования и предлагаемые игровые правила: [основной план](SPECIAL_GROUP_EVENT_PLAN.md).

Обязательный сценарий: во время события на Площади видны боковые «+» для приглашения своих друзей, вне события «+» скрыты. Группа состоит из трёх игроков. Обычная прогулка и PvP 1×1 требуют сначала подтвердить выход из группы. Событие содержит волны по три моба и финального босса; формулы и предметы переиспользуются из текущей боёвки.

Названия новых файлов, таблиц и полей ниже предлагаемые. Расписание, число волн, таймер и награды остаются параметрами контента из основного плана.

Определения добавить в [schema.ts](../../apps/server/src/database/schema.ts). Для JSON использовать существующий подход Drizzle `text(..., { mode: 'json' })` с типами из общего пакета; физически в SQLite это `TEXT`.

Записывается в той же транзакции, что начисление и завершение прохождения. |

Новые внешние ключи ссылаются на `locations.id`, `players.id` и соответствующие новые таблицы. Историю завершённых прохождений не удалять через обычные операции выхода/закрытия события; использовать статусы. Удаление исходных шаблонов мобов не должно разрушать сохранённые снимки боя.

Статусы:

- Группа: `forming`, `active`, `finished`, `disbanded`, `expired`.
- Запись участника: `invited`, `joined`, `active`, `left`, `declined`, `cancelled`, `expired`, `finished`. `joined` блокирует второе лобби; `active` сохраняется и у погибшего наблюдателя до выхода/конца прохождения.
- Прохождение: `active`, `victory`, `defeat`, `aborted`.
- Доступность окна вычисляется из `enabled`, `starts_at`, `ends_at` и серверного времени. Отдельный постоянно синхронизируемый флаг `is_active` не нужен.

Ограничения и индексы:

| Где | Ограничение / индекс |
| --- | --- |
| Окна | `CHECK enabled IN (0, 1)`, целый `min_level >= 1`, `starts_at < ends_at`, положительная версия правил; индекс для поиска по локации, ключу события, включению и времени. Пересекающиеся включённые окна одного события запрещать в транзакции настройки. |
| Группы | Допустимые статусы, неотрицательная целая версия; индекс `(event_window_id, status)` и индекс по сроку жизни; `UNIQUE(leader_player_id, creation_request_id)` для первого создания. Повтор с тем же ключом и другой командой отклоняется по fingerprint. |
| Позиции | `CHECK slot IN (0, 1, 2)` и `ready IN (0, 1)`; частичный `UNIQUE(party_id, slot)` для статусов `invited/joined/active`. |
| Участники | Частичный `UNIQUE(player_id)` для `joined/active` и `UNIQUE(party_id, player_id)` для `invited/joined/active`; индексы по адресату/статусу и сроку приглашения. |
| Прохождения | `UNIQUE(party_id)` не допускает двух запусков одной группы; положительные целые волна/раунд/версии формата, неотрицательная версия состояния; индексы `(status, round_deadline_at)` и `(status, expires_at)`. |
| Награды | `UNIQUE(run_id, player_id)` и неотрицательные целые суммы; индекс по игроку и окну события. Если будет принят лимит одной победы на окно, дополнительно `UNIQUE(event_window_id, player_id)`. |

Приглашение резервирует только позицию в конкретной группе. Пока адресат не принял приглашение, оно не блокирует ему другие лобби или одиночные действия. Вместимость, право приглашения, дружба, HP, положение на Площади и занятость проверяются внутри транзакций. Уникальные индексы дополняют эти проверки.

В `battle_state` хранить:

- Участников по уникальным `fighterId`: команда, связь с игроком/мобом, имя/облик, HP, снимок характеристик, приёмы, кулдауны, статусы и счётчики пассивок.
- Выборы действий с исполнителем и целью; сервер заранее сохраняет выборы ИИ и не публикует их до расчёта.
- События с общим `sequence`, волной, раундом, источником, целью и снимками HP/статусов.
- Обработанные команды с `playerId`, `requestId` и fingerprint, включающим прохождение, волну, раунд, действие, предмет и цель.
- Счётчики использованных зелий, бездействия и причины завершения.

Текущие значения HP и принятые действия имеют один источник в `battle_state`. Колонки волны/раунда/версии нужны для запросов и проверок; если эти значения присутствуют в снимке ответа, они строятся из колонок. HP в `players` синхронизируется после рассчитанного раунда и при выходе/завершении той же транзакцией. По окончании обновляется и `last_regen_time`, чтобы офлайн-время боя не превратилось в накопленную регенерацию.

**Существующие таблицы и миграция**

| Что | Изменение |
| --- | --- |
| `locations` | В существующем JSON `actions` Площади добавить `special_walk`. Новая колонка не нужна. |
| `players` | Переиспользовать `id_the_last_action`: `{ type: 'GroupEventLobby', id: partyId }` либо `{ type: 'GroupEvent', id: runId }`. Новые колонки `party_id/is_in_party` не вводить; право участия определяется таблицей участников. |
| `combat_sessions`, `pvp_sessions` | Оставить текущую схему и формат сохранённых обычных боёв. Групповые прохождения хранить отдельно. |
| `mobs`, `items`, `inventory_items` | Схему не менять. Использовать текущие шаблоны и выдачу предметов. Уникальные профили мобов события хранить в конфигурации окна, чтобы они не попадали в обычные встречи. |
| `friendships`, `events` | Схему не менять. Первая таблица подтверждает дружбу, вторая остаётся журналом локации. |

На этапе планирования свободным номером был `0035`; в реализации используется `0036` после добавленной отдельно миграции хранения сессий. Фактическое имя: `apps/server/drizzle/0036_group_events.sql`. Генерировать через Drizzle с обновлением метаданных, а не переписывать применённые SQL-файлы.

Обнаруженная особенность репозитория: SQL-миграции и `_journal.json` доходят до `0034`, а последний файл snapshot — `0031_snapshot.json`. Перед генерацией нужно согласовать базовый снимок с уже существующими миграциями, чтобы генератор не предложил повторно создать столбцы/изменения 0032–0034. Проверять итоговый SQL: новые пять таблиц и их индексы, без пересоздания таблиц игроков и обычных боёв.

`locations.actions` сейчас создаётся через `ensureLocationsActions()` после миграций. Поэтому миграция новых таблиц не должна обращаться к этому столбцу: на чистой старой схеме его ещё нет. Карточка добавляется в сид `initialize.ts` после существующего вызова `ensureLocationsActions()`. Этот сид уже обновляет `actions` существующих локаций и покроет новую и установленную базу. Список Площади станет `[fight, walk, money, special_walk]`.

Окно события по умолчанию не включать: таблица может оставаться пустой до административной настройки. Структура БД и наличие карточки сами по себе не открывают ивент. Для дат и дедлайнов использовать единую шкалу через адаптер текущего `shared/time.ts`; отображение и ввод времени в админке должны переводиться в эту же шкалу.

**Транзакционные границы**

1. Первое «+»: проверить событие/дружбу/занятость → создать группу и членство лидера → зарезервировать место приглашением → сохранить результат команды. Отправить обновления после commit.
2. Принятие: перепроверить окно/приглашение/свободную позицию/дружбу/членство → подтвердить участника → снять конкурирующие приглашения адресата → сбросить готовность состава → обновить версию.
3. Старт: проверить лидера и троих готовых живых участников на Площади → зафиксировать конфигурацию/характеристики → создать одно прохождение → сменить статусы и `LastAction` всех троих.
4. Ход/дедлайн: перечитать актуальную версию → проверить исполнителя, волну, цель и повтор → сохранить заявку → при готовности разрешить один раунд и одну смену волны → списать реально использованные предметы → обновить HP, версию и дедлайн. Сокеты после commit.
5. Выход: перечитать стадию и членство → выйти из лобби либо прохождения → освободить нужную позицию/действие → очистить только соответствующий `LastAction` → обновить остальных. Одиночная прогулка/PvP выполняется отдельным следующим запросом и повторно проверяет занятость.
6. Победа: завершить прохождение → выдать фактические награды существующими операциями → записать квитанции → освободить участников. Ошибка на любом шаге откатывает всё; повторный запрос не повторяет розыгрыш и начисление.

Если состояние после открытия подтверждения сменилось с лобби на бой, сервер возвращает изменившееся состояние; клиент показывает соответствующее подтверждение выхода. Выход из уже начатого события не подменяется выходом из лобби без уведомления.
