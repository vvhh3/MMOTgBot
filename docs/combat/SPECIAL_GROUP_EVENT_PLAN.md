# Особая прогулка с компанией — анализ и план

Статус: первоначальный план. Реализация завершена; актуальные правила, настройка и проверки описаны в [реализованном событии](GROUP_EVENT_IMPLEMENTATION.md).

Детализация по конкретным файлам, таблицам, полям, индексам и миграциям: [план изменений файлов и БД](SPECIAL_GROUP_EVENT_FILES_AND_DB.md).

**Запрос и ожидаемое поведение**

На Площади (`square`) появляется карточка «Особая прогулка с компанией». Это отдельное событие с ограниченным временем входа. Игрок собирает группу ровно из трёх человек. У каждой группы своё прохождение: обычные волны содержат по три монстра, последняя — одного сильного босса. Каждый игрок управляет своим персонажем и выбирает противника для атаки. Урон, оружие, броня, приёмы, зелья и пассивки работают по существующим правилам.

Уточнение пользователя: существующие «+» по бокам персонажа на Площади используются для приглашения своих друзей в группу. Во время доступного события кнопки активны на свободных местах; вне события они скрыты. Если участник группы выбирает обычную прогулку или PvP 1×1, игра предлагает сначала выйти из группы.

Подтверждены запросом: Площадь, новая карточка, временная доступность, три игрока, волны по три противника, выбор цели, финальный босс, существующая основа боёвки, приглашение друзей через боковые «+», скрытие «+» вне события и обязательный выход из группы перед одиночной прогулкой/PvP.

Не определены запросом: расписание, число волн, уровень входа, сложность для смешанной группы, награды, ограничения повторного участия, таймер действий, смерть и отключения. Ниже для них предложены правила первой версии; они не являются согласованными требованиями.

**Ограничения, которые влияют на объём работ**

- `BattleSide = 0 | 1`, `fighters`, HP, выборы действий, статусы и события представлены парами. В `engine.ts`, `effects.ts` и `passives.ts` противник определяется через `opponent(side)`. Добавления `targetId` в HTTP-запрос недостаточно.
- `combat_sessions` хранит одного игрока и одного моба, `pvp_sessions` — двух игроков. Для группы нужен собственный экземпляр прохождения с сохранённым составом и волнами.
- Таблица `events` — журнал действий в локации. В ней нет расписания или жизненного цикла специальных событий.
- Клиент строит карточки из `location.actions`, а серверный `LocationStateResponse.actions` сейчас перечисляет только `fight` и `walk`. Новую карточку и её временное состояние нужно согласовать в обоих слоях.
- Оба боковых «+» находятся в `Home.tsx` внутри сетки из трёх колонок. У них нет условия видимости и обработчиков. Состояние друзей уже передаётся в `Home` через `friendsOverview`, но для приглашений нужен новый сценарий выбора друга и серверная проверка дружбы.
- Сид в `database/initialize.ts` перезаписывает `locations.actions` при старте. Добавление карточки только SQL-миграцией будет потеряно: требуется обновить и сид.
- `assertOutsideCombat` и `RegenHealth` учитывают только PvE и PvP. Приём обмена может записать `idTheLastAction` без проверки боя; вход в другую локацию тоже сейчас не запрещён во время боя. Новое прохождение нужно включить во все соответствующие проверки.
- Отключение последнего сокета обнуляет `players.currentLocationId`. Состав и доступ к активному прохождению должны определяться сохранённым участием, чтобы возвращение в игру не исключало игрока из группы.
- `BattleScreen` принимает одного игрока и одного противника; `useBattlePlayback` воспроизводит пары HP и статусов. Их можно обобщить, но нельзя подключить к 3×3 без изменений.
- В проекте используется время со смещением через `shared/time.ts`. Расписание, серверное время и дедлайны должны использовать одну согласованную шкалу; прямое смешивание с `Date.now()` даст сдвиг.

| --- | --- |
| Название | «Особая прогулка с компанией». |
| Карточка вне события | Видна с состоянием «Сейчас недоступно» или временем следующего открытия. Создание группы и запуск закрыты сервером. |
| Боковые «+» | По требованию пользователя видны на Площади только во время доступного события. Нажатие на свободное место открывает выбор своего друга. Вне события скрыты; положение основного персонажа по центру сохраняется. |
| Управление доступностью | Администратор задаёт время открытия/закрытия и может отключить набор. Для первой версии достаточно отдельных окон события, без конструктора повторяющихся расписаний. |
| Состав | Три человека: сам игрок и два спутника. Выбор приглашения — из подтверждённых друзей приглашающего. Предлагается разрешить любому участнику заполнять свободные места своими друзьями; создатель остаётся лидером и запускает событие. Вступление добровольное. До старта все трое находятся на Площади, в сети, живы и свободны от другого занятия. |
| Состояние бокового места | Предлагается: свободно — «+»; приглашение отправлено — имя друга и «Ожидаем ответа»; приглашение принято — персонаж друга, имя и HP. Отказ, отмена или истечение приглашения возвращают свободное место. |
| Начало | Три подтверждённых участника нажали «Готов». Лидер запускает бой; сервер заново проверяет весь состав и окно события в одной транзакции. |
| Изменения состава | До старта можно выйти; лидер может исключить участника. Изменение состава сбрасывает готовность. Выход лидера распускает лобби. После старта замены отключены. |
| Обычная прогулка и PvP 1×1 | По требованию пользователя сначала предложить выйти из группы. Отмена сохраняет группу и не запускает действие. Только подтверждённый сервером выход разрешает продолжить одиночный сценарий. Это правило действует и для принятия входящего PvP-вызова. |
| Волны | Для начальной настройки — три волны по три моба и четвёртая волна с боссом. Число и состав хранятся в конфигурации. |
| Сложность | Зафиксировать при старте по максимальному уровню группы; коэффициенты HP, урона и наград настраивать отдельно для события. Экипировку не использовать для скрытого усиления мобов. Значения проверить симуляциями. |
| Раунд | По одному действию от каждого живого игрока и моба. Когда игроки выбрали действия, сервер рассчитывает весь раунд. Защитные приёмы и лечение сохраняют существующие приоритеты; равные приоритеты перемешиваются. |
| Выбор цели | Атаки и ослабления направляются на выбранного живого моба. Защита и лечение применяются к себе, как сейчас. Несколько игроков могут выбрать одну цель. |
| Цель погибла внутри раунда | Если другие противники ещё живы, перенаправить атаку на первого живого по стабильному порядку и явно показать это в журнале. Если волна уже закончилась, оставшиеся действия не исполняются и расходники не списываются. |
| Защита от нескольких атак | Активная защита действует до конца раунда на входящие удары; проверка блока и отражения выполняется на каждый удар. Правила пассивок, реагирующих на защиту противника, должны иметь явный источник/цель. |
| Между волнами | HP не восстанавливается автоматически. Кулдауны, лимит зелья и состояние живых игроков продолжаются; номер раунда сквозной. Следующая волна начинается после полного разрешения текущего раунда. |
| Гибель игрока | Персонаж остаётся наблюдателем, без ходов и без автоматического воскрешения. Оставшиеся могут закончить событие. Поражение — когда не осталось живых игроков; одновременная гибель обеих сторон не даёт победную награду. |
| Таймер | Предварительно 60 секунд на раунд. Пропущенное действие заменяется на `wait` без атаки, лечения и бесплатной защиты. Если вся живая команда пропустила два раунда подряд, прохождение завершается без награды. |
| Отключение | Краткое отключение не удаляет участника; действует тот же таймер. После возвращения восстанавливаются состав, волна, HP и принятый ход. |
| Выход из прохождения | Явный подтверждённый выход исключает персонажа из оставшихся волн и наград; команда продолжает, пока остаются живые участники. Текущий HP сохраняется. Простое закрытие приложения выходом не считается. |
| Закрытие окна | Новые группы и старты запрещены, не начатые лобби закрываются. Начатое прохождение можно закончить в пределах отдельного общего срока. |
| Награды | После победы над боссом: опыт, монеты и персональный бросок добычи каждому не вышедшему участнику, включая погибших. После поражения можно попробовать снова в открытом окне; потраченные зелья не возвращаются. |
| Повторное участие | Предлагается одна победная награда на игрока за окно события. Точный лимит — настройка контента. Защиту от повторной выдачи из-за сетевых повторов обеспечить независимо от этого лимита. |

Действия и цели ИИ выбираются сервером до получения скрытых действий игроков, без подглядывания в их заявки. Для первой версии цель моба выбирается из живых игроков случайно. Босс использует существующие приёмы с отдельным балансом для трёх игроков; новые массовые атаки не являются обязательной частью запроса.

**Сценарий боковых «+» и перехода к одиночному бою**

1. Когда событие открыто, игрок на Площади видит своего персонажа по центру и два боковых места. Пока группы нет, на каждом месте показан активный «+». Если событие закрыто, оба «+» отсутствуют.
2. Нажатие открывает окно «Пригласить друга» на основе `friendsOverview`. В списке — подтверждённые друзья самого приглашающего; уже состоящие в группе не предлагаются повторно. Недоступным друзьям показывается причина. Пустой список сопровождается пояснением.
3. После выбора друга сервер создаёт группу, если её ещё нет, и отправляет приглашение в выбранное свободное место. Создание и приглашение при первом действии выполняются атомарно и с защитой от повтора. Закрытие окна без выбора друга не создаёт группу.
4. На время ожидания место показывает приглашённого друга и статус ответа. При принятии появляется его персонаж; у каждого участника собственный персонаж находится по центру, остальные два — по бокам. Подтверждённые позиции группы сохраняются на сервере, перестановка вида не меняет членство.
5. Карточка «Особая прогулка с компанией» использует тот же состав, что и боковые места: показывает готовность и открывает управление/запуск события. Отдельная вторая группа через карточку не создаётся.
6. При нажатии «Пройтись» участником группы показать: «Вы состоите в группе. Чтобы прогуляться одному, сначала выйдите из группы». Кнопки — «Остаться в группе» и «Выйти и прогуляться». При подтверждении дождаться выхода и только затем отправить обычную прогулку один раз.
7. При выборе PvP показать аналогичное сообщение и кнопки «Остаться в группе» / «Выйти и продолжить». После успешного выхода открыть существующий выбор PvP-противника; сам бой начинается по прежним правилам приглашения. Для входящего вызова после выхода повторно проверить, что приглашение ещё действительно, и продолжить принятие.
8. Для лидера пояснить в подтверждении, что его выход распустит лобби. Если прохождение уже началось, использовать выход из прохождения с указанием потери участия в событии и победной награды. Ошибка выхода не запускает одиночный бой. Если состояние поменялось с лобби на активное прохождение, обновить подтверждение, а не выполнять другой вид выхода молча.

Серверные маршруты обычной прогулки, создания и принятия PvP возвращают `409` с кодом `PARTY_EXIT_REQUIRED`, пока игрок числится в группе/прохождении. Проверять обе стороны при фактическом запуске дуэли. Сервер не исключает игрока автоматически по запросу прогулки или PvP. После выхода обычная проверка занятости выполняется снова: принятие новой группы в другой вкладке не должно позволить обойти ограничение.

**Архитектура изменений**

Сохранить модульный монолит, Express, SQLite/Drizzle, Socket.IO и текущую авторизацию. Новый игровой домен разместить в `apps/server/src/modules/group-events/`, клиентские экраны и API — в `apps/client/src/features/group-events/`, контракты — в `packages/shared/src/contracts/group-events.ts`.

Для первой версии достаточно пяти новых сущностей; имена таблиц рабочие:

1. `group_event_windows`: отдельное окно события на Площади, включение набора, начало/конец, правила входа, конфигурация волн и наград, версия правил.
2. `event_parties`: лидер, окно события, состояние сбора, версия состава и сроки лобби.
3. `event_party_members`: приглашения и участие, позиция в группе, подтверждение, готовность, состояние выхода. Ожидающее приглашение временно резервирует выбранное место в этой группе, но не делает адресата участником и не резервирует его членство во всех группах. Уникальные частичные индексы защищают позицию от одновременных приглашений и запрещают игроку иметь два текущих подтверждённых членства; вместимость проверяется в транзакции. Отказ, отмена и истечение приглашения освобождают место.
4. `group_event_runs`: одно прохождение на группу, неизменяемый снимок трёх игроков, всех волн и наград, текущая волна, HP, раунд, дедлайн, версия состояния, журнал и обработанные команды.
5. `group_event_rewards`: квитанции фактически выданных победных наград участника; уникальность `(runId, playerId)` исключает повторную выдачу. Если принят лимит одной победы на окно, добавить соответствующее ограничение по `(eventWindowId, playerId)`. Поражения фиксируются в прохождениях и не занимают лимит победной награды.

Состав, боевые параметры и правила наград фиксируются при старте; последующие правки конфигурации не меняют начатое прохождение. Использовать существующие шаблоны мобов, создавая отдельные боевые экземпляры с уникальным `fighterId` для каждой волны и позиции. Три одинаковых моба имеют разные HP и идентификаторы. Уникальные враги события не должны попадать в случайную обычную прогулку: для первой версии хранить их определения в конфигурации события, используя тот же формат боевого профиля.

Для группового состояния нужны `fighterId`, `team`, связь с игроком/шаблоном моба, HP, характеристики, приёмы, кулдауны, статусы и выбранное действие. В действии — `actorId`, `moveId`, `targetId`; в запросе также `runId`, `wave`, `round`, `expectedVersion`, `requestId`. Персонаж-исполнитель определяется авторизованным участником, а не произвольным ID из клиента.

Событие журнала хранит `actorId`, `targetId`, сквозной `sequence`, волну, раунд и снимок HP/статусов участников. Идентификаторы не переиспользуются между волнами. Победа над отдельным мобом не завершает раунд или прохождение, пока не проверено состояние команд.

Общий боевой расчёт расширить на явных участников и цели: расчёт одного действия, реакции пассивок, расходование защиты, завершение раунда. Существующие `resolveRound` и `resolveFailedEscape` оставить совместимыми обёртками для 1×1. Внешние DTO обычного PvE/PvP и сохранённые состояния должны продолжить читаться через адаптер. Изменения выполнять с проверкой существующих тестов.

Не запускать нынешний `resolveRound` отдельно для каждой пары: это повторно продвинет кулдауны, яд и другие эффекты, нарушит порядок действий и условия победы. Периодические эффекты и истечение статусов выполняются один раз на общий раунд; гибель одного из шести участников не должна прекращать эффекты остальных.

Отдельно определить поведение существующих пассивок, в которых используется единственный `opponent`: эффекты после попадания относятся к фактической цели удара; реакции на входящее действие — к его источнику. Для побочных враждебных эффектов защиты/зелья без входящего удара предусмотреть явную дополнительную цель из живых врагов; интерфейс запрашивает её только у соответствующего предмета/приёма. Эти эффекты не должны случайно становиться массовыми.

Существующие `MovePanel`, `BattleConsole`, индикаторы статусов, инвентарь и анимации адаптировать через более узкие общие пропсы. Для сцены добавить поддержку команд и выбора цели, сохранив обычный вид 1×1. Воспроизведение событий обобщить с пары HP до участников по ID. На мобильном экране показать три компактные карточки союзников и три карточки противников; на волне босса — одну крупную карточку противника.

При каждом переподключении клиент запрашивает актуальное состояние по HTTP. Более старые версии из запоздавших HTTP/socket-ответов игнорируются. В `LastAction` добавить отдельные виды лобби и прохождения; `idTheLastAction` служит указателем, а источником права участия остаются таблицы группы и прохождения.

**Порядок реализации и проверяемый результат этапов**

1. **Контракты и миграции.** Добавить сущности, индексы, типы состояния и жизненный цикл. Сгенерировать миграцию новых таблиц; карточку `special_walk` добавить только для `square` через существующий сид после `ensureLocationsActions()`. Миграция не должна обращаться к `locations.actions`, поскольку на чистой базе этот столбец пока создаётся после миграций. Проверить новую и существующую базы: данные и незавершённые обычные бои сохраняются.
2. **Доступность события.** Серверная проверка окна, минимальная административная настройка и неактивная карточка с объяснением. Конец окна запрещает старт даже при открытом старом интерфейсе. Начатые прохождения продолжаются.
3. **Сбор группы.** Приглашения своих друзей через боковые «+», подтверждения, готовность, выход, исключение, тайм-аут лобби. Проверять подтверждённую дружбу с отправителем на сервере при приглашении и принятии. Серверная группа вмещает максимум три подтверждённых игрока; старт требует ровно трёх. Все мутации состава транзакционные; одновременные приглашения/принятия не занимают одну позицию дважды и не создают четвёртое место или два членства.
4. **Общий боевой расчёт.** Выделить переиспользуемые правила текущего движка, обобщить участников, выбор целей, реакции пассивок и завершение раунда. Проверить 3×3 и 3×1; все текущие сценарии 1×1 сохраняют поведение.
5. **Прохождение волн.** Атомарный старт, фиксация контента и характеристик, переходы волн, действия ИИ, смерть, таймеры и финальный босс. Расчёт запускается один раз после последнего нужного выбора или истечения срока.
6. **Интеграция занятий и восстановления.** Учесть новый бой в запрете экипировки, продажи занятой экипировки, изменения характеристик, обычного лечения и регенерации. Проверять занятость с обеих сторон при старте/принятии PvP и обмена, а также при старте прогулки и казино. Для прогулки и PvP участника группы возвращать `PARTY_EXIT_REQUIRED`; клиент предлагает подтверждённый выход и продолжает только после успеха. Включить входящие PvP-вызовы и прямые HTTP-запросы. Во время лобби запретить другие занятия; смена экипировки/характеристик сбрасывает готовность, уход с Площади снимает участие. Во время прохождения переход в другую локацию запрещён. Проверки выполняются в момент мутации, а не только при отображении кнопки.
7. **Клиентский сценарий.** Условная видимость боковых «+» в `Home.tsx`, окно выбора своего друга, состояния ожидания и отображение принятых спутников, карточка, лобби на три места, готовность, сцена командного боя, выбор цели и приёма, общий журнал, индикатор «ход принят», номер волны, таймер и экран результата. Подключить единое подтверждение выхода к `WalkCard`, `FightCard`, выбору противника и принятию входящего PvP. Повторно использовать существующие компоненты и стили. Проверить читаемость и выбор цели в Telegram Mini App на узком экране.
8. **Награды и завершение.** После босса одной транзакцией завершить прохождение, выдать фактическую добычу, опыт и монеты, сохранить квитанции наград, освободить занятость игроков. Отправить сокеты после commit. Для первой версии прогрессировать существующие `collect/loot` по фактически выданным предметам; зачёт командных убийств и отдельный квест события добавить только после определения его правил.
9. **Проверки и баланс.** Добавить серверные сценарии, выполнить регрессию и проверить троих клиентов одновременно. Настроить волны и босса по результатам прохождений разными составами и экипировкой.

Этапы 4–6 составляют основную техническую сложность; добавление карточки и лобби само по себе не даёт работающего командного сражения.

**Критерии приёмки**

- Карточка есть только на Площади. Закрытое событие нельзя запустить прямым запросом; открытое доступно по правилам входа.
- Вне события боковые «+» скрыты. Во время события на Площади свободные места показывают активные «+»; основной персонаж остаётся по центру. Серверное закрытие события убирает возможность приглашать даже в уже открытом окне выбора друга.
- «+» открывает подтверждённых друзей приглашающего. Первый выбор создаёт одну группу и одно приглашение; отказ от выбора ничего не создаёт. Ожидание, принятие, отказ, отмена и истечение приглашения корректно обновляют боковое место у всех участников.
- Участник группы не начинает одиночную прогулку и PvP до подтверждённого выхода. Отмена и ошибка выхода сохраняют группу и не продолжают действие. После выхода прогулка запускается один раз, а PvP открывает существующий выбор противника или продолжает действующий входящий вызов.
- Прямой запрос прогулки/PvP участником группы получает `PARTY_EXIT_REQUIRED` без выхода и побочных эффектов. Одновременный запуск события и подтверждение выхода обрабатываются согласованно; новое членство в другой вкладке также блокирует одиночный бой.
- Запуск возможен только для трёх уникальных подтвердивших готовность игроков. Одновременные нажатия запуска создают одно прохождение.
- Две группы проходят независимые волны: HP, цели и награды не пересекаются.
- Три одинаковых моба в одной волне различаются по ID. Игроки могут атаковать одного или разных мобов.
- Погибшие участники не совершают действия и не задерживают следующий раунд. Смерть одной цели не завершает бой всей команды.
- Защита, крит, отражение, яд, щит, лечение и кулдауны работают на правильных участниках. Конец раунда не выполняется повторно на каждую пару бойцов.
- Одновременные ходы трёх игроков принимаются из одного снимка состояния. Повтор запроса не повторяет урон, списание зелья, смену волны или награду. Тот же `requestId` с другой целью отклоняется.
- Цель другого прохождения, союзник или отсутствующий участник не могут использоваться для обычной атаки.
- Тайм-аут и последний ход, пришедшие одновременно, разрешают раунд один раз. Чтение состояния и переподключение не продлевают дедлайн.
- Перезагрузка страницы и перезапуск сервера сохраняют прохождение и уже принятые действия. Сброс `currentLocationId` при отключении не мешает возврату в свой бой.
- Действующая группа или прохождение не теряются при принятии старого приглашения на обмен/PvP. В бою нельзя восстановить HP через обычную регенерацию или изменить сборку.
- Победа над боссом выдаёт каждому допустимому участнику его награду один раз; повторы после перезапуска тоже безопасны. Поражение, тайм-аут и выход не выдают победный лут.
- Закрытие окна запрещает новые старты, но не обрывает начатый бой. Отдельный срок прохождения освобождает заброшенные сессии.
- Регрессия: обычная прогулка Площади, PvP, экипировка, зелья, обмен, квесты и казино сохраняют прежнее поведение.

Для реализации использовать текущие тесты `battle-engine`, `battle-effects`, `pvp`, `square-encounters`, `loot`, `locations`, `weapons`, `quests` и `casino`; новые сценарии разместить рядом. Основные команды: `npm run typecheck`, `npm test --workspace @mmobot/server`, `npm run build:prod`. Добавить целевые клиентские проверки обобщённого воспроизведения событий и выбора цели; ручной прогон выполнить в трёх отдельных сессиях.

На этапе первоначального анализа сборка и тесты не запускались. Результат последующей реализации описан в отдельном документе выше.

**Ожидаемый результат реализации**

Во время события игрок на Площади приглашает друзей через существующие «+» по бокам своего персонажа. После принятия приглашений видит товарищей на боковых местах, готовность 3/3 и запускает общее прохождение через карточку события. Все трое видят одну волну и одни HP противников, каждый выбирает собственную цель и приём. Команда зачищает волны, побеждает сильного босса и получает персональные награды. Между окнами события боковые «+» скрыты и новый вход закрыт; начатые бои можно восстановить и закончить. Для обычной прогулки или PvP игра сначала предлагает выйти из группы и продолжает только после подтверждённого выхода.
